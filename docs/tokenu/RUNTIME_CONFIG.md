# TokenU Runtime Configuration Baseline

**Scope:** OmniRoute core PoC deployed at `tokenu.pro`
**Baseline date:** 2026-09-07
**Purpose:** document the effective runtime configuration model without storing secret values.

This document complements `POC_BASELINE.md` and `RUNTIME_RECOVERY.md`. It records which runtime variables matter, which are present in the current Hostinger process, how startup resolves secrets, and which behaviors must be hardened before a commercial TokenU deployment.

No credential values, API keys, passwords, encryption keys, or hosting account identifiers are included here.

## 1. Boot order

The relevant startup order is:

1. initialize the database;
2. run `ensureSecrets()`;
3. run `enforceWebRuntimeEnv()`.

This matters because `API_KEY_SECRET` can be restored or generated before runtime validation. Therefore `required: true` in `secretsValidator.ts` means the secret must exist by validation time, not necessarily that an operator must provide it manually.

## 3. Secret validation behavior

`src/shared/utils/secretsValidator.ts` currently validates:

### `API_KEY_SECRET`

- minimum length: 16 characters;
- marked required at validation time;
- used by the current OmniRoute API-key CRC/generator logic;
- description calls it an HMAC secret, while the audited generator currently uses PBKDF2;
- known weak values produce a warning rather than a startup error.

### `JWT_SECRET`

- minimum length: 32 characters when present;
- optional in the validator;
- can be restored or generated by startup logic.

## 4. Storage encryption

`STORAGE_ENCRYPTION_KEY` is the critical secret used by the field-level encryption layer for provider credentials.

Current behavior:

- provider credential ciphertext uses the `enc:v1:` format;
- the key is derived with `scrypt`;
- if the encryption key is absent, runtime encryption can operate in plaintext passthrough mode;
- if encryption fails, the current implementation can return plaintext rather than terminate the write;
- encrypted rows cannot be decrypted with a missing or different key.

The current PoC has `STORAGE_ENCRYPTION_KEY` present in the active process.

For commercial TokenU, missing or invalid storage encryption must fail closed.

## 5. Encryption-key version marker

`STORAGE_ENCRYPTION_KEY_VERSION` is currently a version label, not the cryptographic key itself.

Executable references found:

- `scripts/build/bootstrap-env.mjs`
- `electron/main.js`

Both initialize the value to `v1` when missing. No evidence was found that this value participates in AES key derivation or decryption.

Classification:

- recovery metadata;
- useful for future key rotation and backup mapping;
- not a substitute for `STORAGE_ENCRYPTION_KEY`.

## 6. Client API enforcement

`REQUIRE_API_KEY` controls whether incoming client API traffic requires authentication.

Observed code behavior:

- default feature-flag value is `false`;
- when enabled, unauthenticated or invalid client requests are rejected;
- when disabled, several client endpoints permit anonymous access;
- if feature-flag resolution throws, the compatibility wrapper defaults to requiring authentication.

For any public commercial TokenU API, API-key enforcement must be explicitly enabled and verified during deployment.

## 7. WebSocket bridge secret

`OMNIROUTE_WS_BRIDGE_SECRET` authenticates an internal loopback WebSocket bridge.

Observed behavior:

- generated with `randomUUID()` per process when absent;
- compared using timing-safe logic;
- used for the internal Codex Responses-over-WebSocket path;
- does not need to remain stable across restarts.

Classification:

- internal ephemeral secret;
- security-sensitive at runtime;
- not required as persistent disaster-recovery material.

It was included in the current encrypted runtime-secret backup as a conservative snapshot, but restoration does not require reusing the same value.

## 8. Machine identity salt

`MACHINE_ID_SALT` affects OmniRoute's machine-derived identifier.

Current Hostinger process status: `MISSING`.

When absent, the current implementation can use its built-in default salt. This is acceptable for the internal PoC but should not be part of TokenU customer credential design.

Commercial TokenU client keys must not embed machine identity.

## 10. Authoritative configuration source

The active Hostinger process environment is the effective runtime source of truth.

The build `.env` found under the Hostinger build tree is not authoritative for the active critical secrets: previous safe comparisons showed that important runtime secrets are supplied externally by the hosting/deployment layer.

Do not assume that editing a build `.env` changes the active process configuration.

## 11. Secret drift

The active runtime `API_KEY_SECRET` and `JWT_SECRET` do not match the stale persisted values previously observed in SQLite.

Consequences:

- a database-only restore is not guaranteed to reproduce the active runtime;
- the SQLite file must be treated as sensitive because persisted secret values are recoverable;
- runtime secret backup and database backup are separate recovery artifacts.

The storage encryption key is especially important because existing provider credentials depend on the matching active key.

## 12. Recovery classification

### Must preserve

- consistent SQLite backup;
- matching `STORAGE_ENCRYPTION_KEY`;
- source/build baseline;
- runtime/deployment knowledge necessary to launch the service.

### Strongly recommended to preserve

- active `API_KEY_SECRET`;
- active `JWT_SECRET`;
- `STORAGE_ENCRYPTION_KEY_VERSION` as rotation metadata;
- non-secret deployment configuration.

### Regenerable

- `OMNIROUTE_WS_BRIDGE_SECRET`;
- process-local ephemeral state.

## 13. Production hardening requirements

Before OmniRoute-derived routing is used behind commercial TokenU:

1. require `STORAGE_ENCRYPTION_KEY` in production;
2. fail startup if encrypted data exists but the matching key is unavailable;
3. never fall back to plaintext after an encryption failure;
4. keep secrets in an external secret-management/deployment layer;
5. make the effective `DATA_DIR` explicit;
6. explicitly enable and test API authentication for every public client surface;
7. replace OmniRoute customer-facing API-key format with TokenU high-entropy random credentials stored hash-only;
8. separate client request accounting from upstream retry/fallback attempts;
9. suppress raw model reasoning from normal client responses;
10. document and test secret rotation and full restore procedures.

## 14. Current status

The OmniRoute PoC runtime configuration is sufficiently understood and documented to close the configuration-inventory phase.

The current deployment is suitable as a controlled technical PoC, not yet as the final commercial TokenU security model.

A full disaster-recovery restore test has not yet been performed.
